# 集群云端加速服务设计文档

> 文档状态：目标架构 + 当前实现说明<br>
> 更新日期：2026-08-16<br>
> 当前环境仍为 `staging`，正式 HTTPS 业务网关已启用：
> `https://oneclickvidgen.com/api/v1`。支付、并发和恢复能力达到上线门槛前不切换为
> `production`。具体缺口和实施优先级见
> [《集群端待完善清单》](./集群端待完善清单_2026-08-01.md)。

## 1. 目标与范围

本系统为已经完成的本地视频客户端提供可选的云端 GPU 加速能力。

系统有两种运行模式：

| 模式 | 是否登录 | 是否消耗积分 | 计算位置 |
|---|---:|---:|---|
| 本地 GPU 模式 | 否 | 否 | 用户自己的电脑 |
| 集群 GPU 加速模式 | 是 | 是 | Ray 集群 `.22/.107/.71` |

本设计只覆盖集群云端服务，不改变本地 GPU 模式。用户只有在选择集群加速时才需要
登录、检查配额、充值和扣除积分。

## 2. 总体架构

```text
本地客户端
  | 本地 GPU 模式：不访问云端
  |
  | 云端 GPU 模式：Bearer Token（只允许 HTTPS 业务网关）
  v
Nginx（公网 80/443）
  v
cloud-api（业务控制层）
  |-- auth       用户、登录、Token
  |-- quota      并发和每日配额
  |-- wallet     积分账本
  |-- payment    充值订单和支付回调
  |-- voices     预置音色、用户参考音色
  |-- jobs       云端任务和历史记录
  |-- admin      管理员后台 API
  |-- ray        Ray 调度适配器
  |
  |-- PostgreSQL 用户、订单、账本、任务、审计
  |-- Redis 队列、锁、限流、短期状态
  |-- MinIO 音色、任务结果、视频文件
  v
Ray Head `.93:6379`
  |-- `.22` RTX 5070 Worker
  |-- `.107` RTX 4090 Worker
  `-- `.71` RTX 5090 Worker
```

Ray Serve `8000` 属于内部计算接口。公网客户端不能直接访问 Ray 端口，也不能获得
Ray API Key。公网只暴露 Nginx 的 `80/443`，生产环境使用 HTTPS。2026-08-04 已关闭
Nginx 的公网 `/api/tts/` 转发，公网探测 Ray 内部端口也被云安全组阻断；Ray 部分端口
在主机上的监听范围仍过宽，仍需用主机防火墙落实集群网段白名单。

## 3. 组件职责

### 3.1 cloud-api

唯一的业务入口，负责：

- 用户注册、登录、刷新和撤销 Token
- 参考音色上传、校验、查询、去重和删除
- 云端任务创建、查询、取消和历史记录
- 配额检查
- 积分报价、预扣、结算和释放
- 图片任务由客户端全量入队，服务端按健康账号实时负载铺满上游可用容量；不设置客户端
  并发上限或单用户队列数量上限，上游忙碌时保留排队并自动轮换账号
- 充值订单创建和支付回调验签
- 结果文件授权下载
- 管理员权限和审计
- 调用内部 Ray Serve

第一阶段建议使用模块化单体，不要拆成多个微服务；模块之间通过明确的服务接口
隔离，后续再按负载拆分。

### 3.2 PostgreSQL

保存需要可靠事务的数据：用户、会话、配额、充值订单、积分账本、用户音色、云端
任务、审计日志。数据库必须有定期备份和恢复演练。

### 3.3 Redis

目标用途是任务队列、分布式锁、登录限流、接口限流和短期任务状态。Redis 不是积分
账本的最终来源。当前 cloud-api 任务队列主要使用 PostgreSQL，Redis 由 Ray 状态层
使用；cloud-api 的分布式限流和领取租约尚待实现。

### 3.4 MinIO

保存参考音色、输入文件和最终音频/视频。数据库只保存对象键、大小、哈希和过期时间。
用户上传的原始音频与服务端标准化音频使用不同对象键，均不得使用用户提供的文件名
直接拼接对象路径。下载必须经过 cloud-api 授权，不能把永久公开的 MinIO URL 返回
给客户端。

### 3.5 Ray Adapter

将业务任务转换为 Ray 任务，负责：

- 指定 `tts_service`、`tts_gpu` 等资源
- 传递 `cloud_job_id`
- 等待和收集推理结果
- 处理 Ray 断连、超时和重试
- 将 GPU 使用信息返回计费模块

Ray 层不处理用户密码、充值、积分或管理员权限。

## 4. 用户与认证设计

### 4.1 认证边界

本地模式不需要认证。云端模式的所有业务请求都必须绑定 `user_id`，不能相信客户
端传入的用户 ID。

### 4.2 Token

- 密码使用 Argon2id 或 bcrypt 哈希，禁止明文保存。
- Access Token 建议有效期 15 分钟。
- Refresh Token 使用轮换策略，支持单设备或全设备撤销。
- Refresh Token 只保存哈希值。
- 管理员使用独立角色和更短的会话有效期。
- 生产环境必须启用 HTTPS。

### 4.3 登录模式选择

客户端可以在本地固定端口启动回调服务，例如：

```text
http://127.0.0.1:17832/auth/callback
```

登录成功后通过一次性 code 返回客户端，再换取 Token。不要把系统级密钥打包进
GitHub 客户端。

## 5. 配额与积分

### 5.1 配额

配额用于限制资源滥用，与积分余额分开：

- 最大并发任务数
- 每日任务数
- 每日字符数或分钟数
- 单任务最大字符数
- 单文件最大大小
- 单用户最大排队任务数

“账户父任务并发”和“Ray GPU 实际处理能力”是两个不同概念：

- `max_concurrent_jobs`：单个账户允许占用的任务执行槽。
- 分块调度：父任务中的所有未完成短文块一次性入队，不接收人工并行上限。
- Ray GPU 副本：每个空闲副本主动领取下一个短文块，实际并行度由当前健康 GPU
  副本数自然决定。

父任务是鉴权、积分和结果聚合单位；`chunks[].index` 是真正的调度和下载单位。
任何分块完成后都必须立即写入父任务的部分结果，并在父任务仍为 `running`
时允许客户端下载。

账户并发必须在后台 Worker 领取任务时原子校验，不能只在创建任务接口校验。占槽状态
至少包含 `dispatching`、`running`、`finalizing` 和尚未终止的
`cancel_requested`；`queued` 不占执行槽，但受 `max_queue_jobs` 限制。达到某个用户的
并发上限时，调度器应跳过该用户并继续调度其他用户，避免队头阻塞。

当前实现会在创建任务时检查并发，但 Worker 领取队列任务时没有再次校验；同时在 Ray
仍为 `queued` 时 cloud-api 可能已显示 `running`。该逻辑尚未达到本节目标，修复方案和
验收用例见待完善清单第 3.2、3.3 节。

### 5.2 积分账本

积分必须通过不可变账本管理，不能只修改一个余额字段。账本类型：

```text
recharge       充值到账
reserve        创建任务预扣
consume        任务成功结算
release        任务失败/取消释放
refund         退款
admin_adjust   管理员调整
expire         过期
```

每次变更必须有 `idempotency_key` 和业务引用 ID。积分变更与任务状态变更需要在同一
个数据库事务或可恢复的事务流程中完成。

### 5.3 任务计费

```text
报价 -> 检查余额 -> reserve 预扣 -> 执行 Ray
  -> 成功：reserve 转 consume
  -> 失败：release
  -> 取消：按已产生资源结算或 release
```

实际计费数据由服务端计算，不能相信客户端上报的 GPU 时间或完成状态。
当前定价为：集群 TTS 每开始的 200 个字符收取 0.2 积分；Gemini 按 RunningHub
输入/输出 token 折扣价折算人民币后上浮 5%；文生图与参考图编辑按实际美元成本折算
人民币后上浮 5%。模型与图片结算保留 6 位小数。

## 6. 充值设计

充值必须使用订单和支付平台服务端异步回调：

```text
客户端创建充值订单
  -> cloud-api 返回支付参数/二维码
  -> 用户完成支付
  -> 支付平台回调 cloud-api
  -> 验签、核对订单号和金额
  -> 订单 paid
  -> 写入 recharge 账本
  -> 客户端查询订单状态
```

必须处理：重复回调、金额不符、订单过期、退款、人工补单和支付平台延迟。不要根据
客户端支付成功页面直接增加积分，也不要保存银行卡信息。

支付提供商使用适配器接口，具体微信/支付宝/海外渠道由部署主体和地区决定。

## 7. 参考音色设计

### 7.1 音色类型和引用

云端支持两种音色：

```json
{"type": "preset", "id": "voice_01.wav"}
{"type": "uploaded", "id": "voice_xxx"}
```

- `preset` 是服务端维护、所有有效用户可使用的预置音色。
- 每个启用的 `preset` 在 cloud-api 保存只读试听副本。已登录用户可通过专用接口播放，
  试听不提交 Ray 任务、不扣积分，也不占用 GPU 并发。
- `uploaded` 是当前用户上传的私有参考音色，只能由音色所有者使用。接口查询参数为了
  兼容旧客户端暂时也接受 `custom`，新客户端统一使用 `uploaded`。
- 报价和创建任务只接受音色类型与音色 ID，不接受 MinIO 对象键或任意文件路径。
- cloud-api 必须校验音色存在、状态为 `active` 且当前用户有权使用，Ray Adapter 只接收
  cloud-api 解析后的内部对象引用。
- 创建任务时在任务记录中保存音色 ID、类型、名称和内容哈希快照，避免后续重命名或
  删除影响历史任务审计。

### 7.2 上传和校验

首版使用同步上传和校验流程。上传成功返回的 `voice_id` 可以立即用于报价和任务创建，
不引入异步音色处理状态机。

默认限制如下，部署时可以通过配额策略收紧，但不能由客户端放宽：

| 项目 | 默认限制 |
|---|---:|
| 文件格式 | WAV、MP3、FLAC |
| 单文件大小 | 20 MiB |
| 解码后时长 | 3-30 秒 |
| 单用户自定义音色数 | 20 个 |
| 单用户音色总存储 | 500 MiB |
| 显示名称 | 1-80 个字符 |

服务端不能只根据扩展名或客户端 MIME 判断文件类型。完整流程为：

```text
校验登录、限流和音色配额
  -> 流式接收至隔离的临时对象并限制实际字节数
  -> 计算 SHA-256
  -> 使用可信音频解码器探测真实格式、时长和音频流
  -> 拒绝损坏、纯静音、超限或包含非音频载荷的文件
  -> 标准化为 24 kHz、单声道、16-bit PCM WAV
  -> 写入用户音色记录和 MinIO 私有对象
  -> 返回 active 音色
```

按当前产品要求，客户端和服务端均不再使用 `consent_confirmed` 字段。内容治理、投诉、
封禁和服务条款仍需独立建设，不能依赖一个前端勾选框实现。

### 7.3 幂等和去重

- 上传请求必须携带 `Idempotency-Key`。
- 同一用户、同一幂等键、相同请求重复提交时返回第一次创建的音色。
- 同一幂等键对应不同文件或参数时返回 `409 IDEMPOTENCY_CONFLICT`。
- 同一用户上传相同 SHA-256 的音频时返回已有音色，并标记 `deduplicated=true`，不重复
  占用存储配额。
- 不跨用户复用数据库音色记录或暴露哈希命中结果，防止用户之间的信息泄露。底层存储
  是否做加密后的物理去重属于实现细节，不能改变用户隔离边界。

### 7.4 存储和生命周期

建议的 MinIO 对象键由服务端生成：

```text
users/{user_id}/voices/{voice_id}/source
users/{user_id}/voices/{voice_id}/normalized.wav
```

目标音色状态为 `active`、`disabled`、`deleting`、`deleted`。当前已实现
`active/deleted`；`disabled/deleting`、失败重试和补偿清理仍待完善。删除目标规则：

- 音色被 `created`、`queued`、`running`、`finalizing` 或 `cancel_requested` 任务引用时
  返回 `409 VOICE_IN_USE`。
- 没有活动任务引用时，先将状态改为 `deleting`，再删除 MinIO 对象并软删除数据库记录。
- 对象删除失败必须可重试；记录不能直接消失，否则无法清理孤儿对象。
- 已完成任务保留音色快照，但不能继续读取已删除的参考音频。
- 管理员因违规禁用音色时必须记录原因和审计日志，并阻止新任务使用。

任务创建与音色删除必须锁定同一条 `user_voices` 记录，保证“校验后提交任务”和“删除
音色”不会并发穿透。

预置音色提供受认证的只读试听接口；用户上传的原始参考音频不提供通用下载接口。列表
和详情接口只返回当前用户有权查看的元数据，不能返回 MinIO 对象键、内部签名地址或
其他用户的音色信息。浏览器通过本地后端代理试听，云端 Access Token 不进入浏览器。

## 8. 云端任务状态机

```text
created -> queued -> running -> finalizing -> completed
                      |             |
                      v             v
                   failed       failed

queued/running -> cancel_requested -> cancelled
completed/failed/cancelled -> expired（结果文件过期）
```

创建任务时生成服务端 `cloud_job_id`。客户端可以提供 `client_job_id` 做幂等，但不能
指定最终任务状态、费用或 Ray 节点。

## 9. 数据模型

核心表：

```text
users
user_sessions
user_quota_policies
wallet_accounts
wallet_ledger
recharge_orders
payment_events
user_voices
cloud_jobs
cloud_job_events
job_artifacts
admin_users
admin_audit_logs
```

关键约束：

- `users.email` 或手机号唯一
- `wallet_ledger.idempotency_key` 唯一
- `recharge_orders.provider + provider_order_id` 唯一
- `user_voices.user_id + voice_id` 唯一
- `user_voices.user_id + sha256` 对未删除记录唯一
- `cloud_jobs.user_id` 建索引
- `cloud_jobs.user_id + client_job_id` 唯一
- 所有金额和积分使用整数最小单位，不使用浮点数
- 任务结果和上传文件保存 SHA-256

`user_voices` 目标至少保存：`voice_id`、`user_id`、`display_name`、`status`、原始格式、
解码后时长、标准化参数、原始/标准化对象键、实际字节数、SHA-256、创建时间和删除
时间。当前表只保存名称、状态、格式、大小、哈希、幂等键和时间字段，其余字段需要随
音频深度校验一并补齐。

## 10. 安全设计

- 公网只开放 `80/443`；Ray `6379/10001/10002/10003/11000-11199` 仅内部可达。
- Ray Serve 使用内部服务凭据，不能返回客户端。
- 任务、音色和下载接口检查资源归属，不能仅凭资源 ID 放行。
- 所有支付回调验签并做幂等处理。
- 登录、注册、充值、音色上传、任务创建分别限流。
- 上传文件检查扩展名、MIME、实际字节数、解码内容和时长；处理文件名路径穿越、压缩
  炸弹、畸形媒体和解码器资源耗尽。
- 日志不得记录密码、Token、支付密钥或完整支付回调密文。
- 管理员操作必须写审计日志。
- 结果文件按用户和任务隔离，定期清理过期对象。

## 11. 运维与监控

必须监控：

- Ray Alive 节点和 `tts_gpu` 资源
- Worker 容器重启次数
- 任务队列长度、排队时间、执行时间
- GPU 使用率和显存
- 任务失败率和超时率
- 充值回调失败数
- 音色上传、校验、去重和删除失败数
- 用户音色数量、存储用量和 MinIO 孤儿对象数
- 账本异常和重复幂等键
- PostgreSQL、Redis、MinIO 存储空间

`.93`、`.22`、`.107`、`.71` 的 Ray 节点配置变更必须保留记录。退役 Worker 必须
先停止自动重启容器，再清理 Ray 会话中的旧节点记录。

### 11.1 2026-08-16 实际运行态与网络现状

本节是巡检快照，不改变前文的目标架构定义：

- Ray GCS 实际只有 .93 Head 与 .107 RTX 4090 Worker 两个 Alive 节点；.22、.71
  当前不提供资源。GCS 还保留 13 条历史 Dead 节点记录，容量统计必须按 Alive 状态过滤。
- 当前总资源为 16 CPU、1 GPU；巡检时使用 8 CPU、1 GPU，无 Pending Demand 和
  Recent Failure。
- .93 的 Nginx、cloud-api、普通/视频任务 Worker、PostgreSQL、Ray Head 及 .107 控制
  通道均为 active，systemd 无失败单元。
- 官网公网首页、工作台和 GET /api/v1/health 均返回 200；Cloud API 监听
  127.0.0.1:8080，官网静态目录为 /var/www/oneclickvidgen。
- Ray TTS 健康接口返回 ok=true、dispatcher ready，模型与音频收尾依赖均 ready，配置
  2 个 GPU Replica。
- .107 的 5 个正式容器均运行，enrollment API 与 PostgreSQL healthy；RTX 4090 显存
  使用约 17.5/24.6 GiB，巡检时 GPU 利用率约 5%。
- .93 根分区使用 24%，可用内存约 4.5 GiB；.107 根分区使用 8%，可用内存约 24 GiB。

.93 的 wg-ray 地址为 10.250.0.1，.107 为 10.250.0.3。2026-08-16 实测 5/5 无丢包、
RTT 约 33 ms，.107 的 18443（enrollment API）、18444（模型分发）和 5432（enrollment
PostgreSQL）均可由 .93 直达。

当前业务仍通过 ray-platform-107-tunnel.service 在 WireGuard 上再建立 SSH 本地端口
转发：25432 到 5432、28443 到 18443、28444 到 18444。该服务累计重启计数已达到
1051，当天日志出现长时间 SSH 超时、一次后端拒绝连接；官网日志也记录过一次 enrollment
上游超时和一次连接重置。后续应切换为 10.250.0.3 的 WG 直连，并短期保留 SSH 路径
作为回退。

需要特别区分：当前 .93 到 10.201.211.107 的路由本身也经过 wg-ray，因此现状是
SSH over WireGuard。移除 SSH 层能减少长连接、端口转发和重连故障，但不能解决 .107
宿主机休眠、WSL 重启或 WG 离线；宿主机不休眠、WSL/WG/容器自动恢复和告警仍是必要条件。

新增监控项：WireGuard 最新握手时间、10.250.0.3 三个端口的可达性、.107 宿主机/WSL
启动状态，以及 SSH 回退隧道的重启次数。

## 13. 验收标准

1. 本地 GPU 模式不登录、不调用云端、不产生积分记录。
2. 云端模式未登录时只能访问公开健康检查，不能创建任务。
3. 云端任务创建会原子地检查配额和预扣积分。
4. Ray 失败不会永久扣除预扣积分。
5. 支付重复回调不会重复增加积分。
6. 用户只能查看和下载自己的任务。
7. 用户只能查询、使用和删除自己的自定义音色，不能通过音色 ID 越权访问。
8. 重复上传相同音频不会重复创建对象；幂等键冲突会明确拒绝。
9. 非法格式、伪造 MIME、超限、损坏和纯静音音频不能进入正式音色存储。
10. 被活动任务引用的音色不能删除，删除失败可重试且不会留下无主记录。
11. 管理员调整积分和禁用音色一定产生审计记录。
12. Ray 内部端口不暴露公网，公网业务只经过 HTTPS 网关。
13. 同一用户快速或并行提交任务时，实际占槽任务数永远不超过账户并发上限；其他用户
    不会被队头任务饿死。
14. cloud-api Worker 在领取后、提交 Ray 前后任意时刻崩溃，任务都能自动恢复到可运行
    或明确终态，不会永久卡在无 `ray_job_id` 的运行状态。
