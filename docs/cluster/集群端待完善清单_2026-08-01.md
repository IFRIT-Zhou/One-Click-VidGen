## 2. 三种“并发”必须分清

| 名称 | 含义 | 当前值/来源 |
|---|---|---|
| 账户任务并发 | 单个账户同时占用云端执行槽的任务数 | 前端显示 `running_jobs/max_concurrent_jobs`，默认上限 2 |
| 单任务分块并行 | 一个 TTS 任务同时处理多少个文本块 | 请求中的 `scheduling.max_parallel_chunks` |
| 集群全局任务并发 | Ray Dispatcher 同时执行多少个完整任务 | 当前 `MAX_ACTIVE_JOBS=1` |

当前前端的“并发 0/2”不是 GPU 数，也不是文本分块数。左侧数字由 cloud-api 统计
`running` 和 `finalizing` 任务，右侧数字来自账户配额。

目前存在两个口径问题：

1. cloud-api 在创建任务时检查并发，但后台 Worker 从队列取任务时没有再次按账户原子
   校验，因此快速提交多个任务可能突破账户上限。
2. cloud-api 在调用 Ray 前就把任务标记为 `running`，而 Ray 返回的初始状态仍可能是
   `queued`。所以界面的“运行中”可能包含正在 Ray 队列等待的任务。

### 3.2 完成账户并发与排队调度闭环

建议明确以下状态：

```text
queued -> dispatching -> running -> finalizing -> completed
              |             |             |
              v             v             v
           queued/failed  failed       failed
```

其中 `dispatching` 表示 cloud-api Worker 已获得执行租约、正在向 Ray 提交，但尚未拿到
Ray Job ID。需要完成：

- [ ] 创建任务只检查总活动/排队上限、每日额度和积分，不把“当前并发已满”误当成不能
  排队。
- [ ] Worker 领取任务时锁定用户配额行，并在同一事务中重新统计该用户占槽状态。
- [ ] `running`、`finalizing`、尚未终止的 `cancel_requested` 和 `dispatching` 都占用
  账户并发槽。
- [ ] 达到 `max_concurrent_jobs` 时跳过该用户，继续选择其他用户可运行的最早任务，
  防止一个账户阻塞全局队列。
- [ ] 使用 PostgreSQL `FOR UPDATE SKIP LOCKED`、用户级 advisory lock 或等价机制，
  保证多个 cloud-api Worker 同时运行时不会超发。
- [ ] 向 Ray 提交成功后原子写入 `ray_job_id`；提交失败按可重试/不可重试错误分类。
- [ ] 账户摘要增加 `queued_jobs`，并明确 `running_jobs` 的统计状态集合。
- [ ] 根据真实 GPU 压测决定 Ray `MAX_ACTIVE_JOBS`，并在管理接口展示全局容量；不要
  默认把“3 张 GPU”直接等同于“3 个完整任务并发”。

最低测试：同一用户连续提交 5 个任务时运行槽永远不超过 2；第二个用户仍能获得执行
机会；完成、失败和取消后槽位都会释放；两个 Worker 并行领取也不能超发。

### 3.3 修复任务崩溃窗口和自动恢复

当前 Worker 先把任务改成 `running`，再通过 HTTP 调用 Ray。进程若在两步之间退出，
会留下 `running` 且没有 `ray_job_id` 的永久卡死任务。需要：

- [ ] 为任务领取增加 `lease_owner`、`lease_expires_at`、`dispatch_attempts` 和
  `next_retry_at`。
- [ ] 定时扫描过期 `dispatching`、长期无心跳 `running` 和未知 Ray Job。
- [ ] 使用 `cloud_job_id` 作为 Ray 幂等键；恢复时先查询，再决定重提，避免重复推理和
  重复扣费。
- [ ] 区分网络超时、Ray 4xx、Ray 5xx和内部数据错误，配置指数退避与最大重试次数。
- [ ] Worker 重启后执行 reconciliation，最终把任务推进到可运行或终态。
- [ ] 取消请求只有在 Ray 确认取消或任务自然终止后才释放并发槽。
